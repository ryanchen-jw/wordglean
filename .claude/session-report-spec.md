# LinguaApp 子專案 session 回報規範

> 實作端（子專案新 session 或執行長在本對話接手）與執行長共用的驗收契約。
> 每次 daily-brain 派工 prompt 都 ref 本檔；實作端開工前先讀。

## 原則

> 分工：本檔＝「回報長什麼樣」（內容與版型）的單一權威；「何時算完成／該熔斷」＝`harness/02-judgment-matrix.md`（回報完成前先對 §2 逐條自檢）；派工 prompt 的約束句＝`harness/03-delegation-templates.md` §0。

- 每個階段（Round 1 / Stage N / 結案）回到執行長時用統一格式；每份 ≤30 行、30 秒可掃完；代碼引用一律 `路徑:行號`
- **每份回報開頭必附 TL;DR**：3 行白話總結＋1 行「執行長現在要做什麼」，讓執行長 30 秒可拍板
- TL;DR 用白話寫（避開術語、套件名、function 名；技術細節在下方各區段保留原文，看不懂時往下對照）
- 只寫 diff 看不出的資訊（執行長會自己看 worktree 分支或工作區 diff）；重點放「需要決策」與「風險」

## 場景速選表

| 情境 | 用 |
|---|---|
| Round 1 計畫列完、尚未動工 | 場景 1 |
| 某 stage 跑完、等審 diff | 場景 2 |
| 執行中卡住、要執行長選路 | 場景 3 |
| 硬故障、無法繼續 | 場景 4 |
| 有 side effect 的任務收尾 | 場景 5（附在場景 2/4 內） |
| 今日做不完、要留續作交接 | 場景 6 |
| 走查官交 UI 走查報告 | 場景 7 |

## 共用骨架（場景 1–4 同一版型）

組裝法＝下方骨架 × 各場景差異（狀態字、中段區段、結尾句）；完整成品長相以場景 2 範例為準。`<階段>`＝Round 1 / Stage <N>；TASK-ID 取自派工 prompt 的 backlog 任務；一任務一份回報，涵蓋多任務時拆成多份。

```markdown
# Task：<TASK-ID>－<ProjectName>－<階段>｜<狀態>

## TL;DR（白話 3 行）
- <一句話：發生什麼／做了什麼（白話）>
- <一句話：影響什麼／打算怎麼做>
- <一句話：風險、意外、或實作端傾向>

**執行長現在要做的事**：<一行：審什麼／選什麼>

<中段：依各場景「中段區段」順序>

---
<結尾等待句：見各場景>
```

## 場景 1：Round 1 計畫回報（只列計畫、禁止改檔）

- 狀態：`📋 計畫`；執行長要做的事：審本計畫 → 核准進 Round 2，或調整方向
- 中段區段（依序）：
  - **現況理解**：對任務的解讀、查到的現有工具／現況（2–4 行）
  - **計畫表**：表格 `| Stage | 做什麼 | 預期產出 | 預計動到的檔案 |`
  - **風險與 Unknown**：表格 `| # | 項目 | 影響 | 緩解 |`
  - **需要執行長決策的問題**：若有；每題附選項與建議
- 結尾句：`等待執行長審核，本輪未改任何檔案。`

## 場景 2：Stage N 完成回報

完整範例＝格式錨，照抄組裝（--bg worker 的回報由執行長經 `claude logs` 收取；人肉流程回本對話）：

```markdown
# Task：<TASK-ID>－<ProjectName>－Stage <N>｜✅ 完成

## TL;DR（白話 3 行）
- <一句話：這個 stage 做完了什麼（白話、不用術語）>
- <一句話：影響到什麼（功能 / 檔案 / 資料 / 使用者體感）>
- <一句話：有沒有意外、副作用、要注意的事>

**執行長現在要做的事**：審 diff → 核准進下一 stage（或要求調整）。

## 本 stage 完成的事
- ...

## 改動／新增的檔案
- `path/to/file`（一句話摘要）

## 產出 artifact
- 文件／測試報告／待 commit 目標 — 路徑
- app UI 變更:附**視覺 smoke** 本地 report 資料夾路徑＋`show-report` 指令、mock 值 vs 真實值、**未上雲**確認(見 `harness/06-uiux-visual-smoke.md`)

## 需要執行長確認才進下一 stage 的事項
（若有）

---
等待執行長審 diff、核准後進下一 stage。
```

## 場景 3：卡住 / 需要決策（執行中遇到無法自決的情境）

- 狀態：`🟡 需要決策`；執行長要做的事：在下方選項裡選一個，或給其他指示
- 中段區段（依序）：
  - **卡點**：描述情境、為什麼無法自決
  - **選項**：表格 `| # | 選項 | 代價 / 風險 |`
  - **建議**：實作端傾向哪個，理由 1–2 句
- 結尾句：`等待執行長選定選項。`

## 場景 4：Blocker（不可繼續）

- 適用：外部依賴卡死、環境異常等硬故障；狀態：`🔴 Blocker`；執行長要做的事：決定轉 pending、介入排查、或換方向
- TL;DR 第 3 行固定寫：環境是否清乾淨、有無殘留
- 中段區段（依序）：**故障現象**／**已嘗試的步驟**／**根因推測**（可推測，標明非定論）／**環境還原狀態**（附場景 5 勾選）
- 結尾句：`實作端停工，等執行長決策後續。`

## 場景 5：環境還原確認（QA / 測試類任務必填）

有 side effect 的任務（改 .env、啟動服務、寫 DB）結束前必附此勾選，放進場景 2／4 回報內（對應 `02 §2` 完成判準的環境還原項）：

```markdown
## 環境還原確認
- ✅ / ❌ `.env` 已還原
- ✅ / ❌ 臨時啟動的服務已關閉
- ✅ / ❌ 測試資料已清理 / 無殘留
- ✅ / ❌ `git status` 無未預期改動
```

## 場景 6：pending 檔產出（今日未做完 → 下次續作）

pending 內容規格以本場景為唯一權威（daily-brain Step 6.2 為指標）。stage 未跑完或任務整體延後，必留：

```
<Project>/docs/pending/YYYY-MM-DD-<topic>/pending.md
```

`pending.md` 必含：今日進度（做到哪）／未完成原因（卡點、時間、策略決定）／續作執行指引（具體下一步、需讀哪些檔）／執行長當日拍板的決策摘要。
若有具體 bug → 改用 `<Project>/docs/pending/YYYY-MM-DD-<bug>/proposal.md`（修法提案）。

## 場景 7：UI 視覺走查回報（has-ui 任務、走查官交執行長）

走查官（03 模板 E）交執行長；**報告本體格式權威＝`harness/05-ui-visual-review.md` §7**（受影響畫面、挑刺清單逐項 ✓/✗/NA、✗ 分 P0/P1/P2），本場景只定外包裝：

- 標題列：`# Task：<TASK-ID>－<ProjectName>－UI 視覺走查｜🖼️ 報告`＋TL;DR 3 行（走查範圍與可否 merge／P0-P2 數與最嚴重項／走查卡點）
- 執行長要做的事：看分級 → P0 退回修、P1 當輪修或立案、P2 記 backlog
- 走查官特有欄（05 §7 之外必附）：**截圖組**（絕對路徑）／**總評**（可 merge / 需修 P0 後再驗）／**verdict 摘要**（≤6 行，供 07 落檔）
- 本關 report-only：走查官只出報告，修不修由執行長裁量

## 執行長端驗收原則

- 實作端回報對應場景 1–4 之一；走查官對應場景 7
- 執行長以 diff 校驗「改動檔案」項誠實（--bg worker：`git -C <Project> diff <預設分支>..worktree-<topic>`；人肉／主對話實作：工作區 `git status` / `git diff`）
- blocker / QA 情境必附場景 5 勾選；未完成任務留了場景 6 pending 檔才算合格結案
- 落地＝已 squash-merge 進主線；worker 在 worktree 分支的 commit 只是工作快照
