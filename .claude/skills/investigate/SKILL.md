# investigate — 根因調查與修復

## 鐵律

**沒找到根因，不准修。**
只修症狀會變成打地鼠：每個沒打到根因的修補，都讓下一個 bug 更難找。

**修 bug ＝ 先寫出能重現的測試（現在是紅的），再讓它通過。**
沒有紅燈測試的修補，等於無法證明修好了什麼。

## Phase 1：收集症狀與重現

1. **讀完整症狀**：錯誤訊息、stack trace、重現步驟、發生環境（本機／測試機／正式）。資訊不足就問使用者，一次只問一個問題。
2. **確定性重現**：找出能穩定觸發的最小步驟。
   - 重現不了 → 不要猜，繼續收集證據（加 log、問發生頻率與條件）。
   - 牽涉網頁畫面 → 用 `browser` skill 重現並截圖（截完自己 Read 看）。
3. **把重現寫成測試**：
   - 照專案既有測試風格（先讀 2–3 個最近的測試檔，命名、斷言、setup 方式照抄）。
   - 測試斷言的是「正確行為」，不是「不會 throw」或「有 render」。
   - **跑一次，確認它是紅的、而且紅的原因就是這個 bug**。紅在別的地方（import 錯、環境缺）不算。
   - 真的寫不出自動化測試（純視覺、外部服務、時序極難控制）→ 寫下手動重現腳本並說明原因，標記為 DONE_WITH_CONCERNS 候選。

## Phase 2：找根因

1. **從症狀往回追程式路徑**：Grep 所有相關引用，Read 讀懂邏輯，畫出資料流（哪個輸入 → 經過哪些函式 → 在哪一行變錯）。
2. **看最近的變更**：
   ```bash
   git log --oneline -20 -- <相關檔案>
   ```
   以前會動、現在不會動＝回歸，根因多半就在那段 diff 裡（`git bisect` 可用）。
3. **修可疑的既有邏輯之前，先坐實來由**：
   ```bash
   git blame -L <起>,<訖> <檔案>
   git show <commit>          # 讀 commit 訊息與當時的完整 diff
   ```
   再查相關的設計文件、issue、PR 描述、程式註解。
   - 確認是**刻意設計** → 不是 bug，回頭重新定義問題（可能是需求變了，要問使用者）。
   - 確認是**疏失** → 在報告中寫明依據（哪個 commit、為什麼判定非刻意）。
   - **無法判定** → 停下來問使用者，不要自己決定。
4. **比對常見模式**：

   | 模式 | 特徵 | 去哪找 |
   |---|---|---|
   | 競態 | 時好時壞、跟時序有關 | 共享狀態的並行存取 |
   | null／undefined 傳遞 | TypeError、找不到屬性 | 可選值缺少防護 |
   | 狀態損壞 | 資料不一致、只更新一半 | 交易、callback、hook |
   | 整合失敗 | timeout、回應格式不符 | 外部 API、服務邊界 |
   | 設定漂移 | 本機好、別的環境壞 | 環境變數、feature flag、DB 狀態 |
   | 快取過期 | 顯示舊資料、清快取就好 | 伺服器快取、CDN、瀏覽器、Service Worker |
   | 時區／日期 | 跨日、跨時區才錯 | UTC 與本地時間轉換、排程 |

   同一區塊反覆出 bug＝架構問題的訊號，不是巧合，要在報告提出。
5. **外部搜尋**（模式表對不上時）：只搜「框架＋通用錯誤類型」。**先去敏**：拿掉主機名、IP、路徑、SQL、使用者資料。
6. **產出一句假設**：「根因假設：＿＿，因為＿＿」——必須具體、可驗證。

## Phase 3：驗證假設

1. 在疑似根因處加暫時性 log／斷言，跑重現測試，看證據是否吻合。
2. 假設錯了 → 回 Phase 1 收更多證據，不要用猜的換下一個。
3. **三振規則**：連續 3 個假設都不成立就停下，問使用者：
   - A) 繼續查（附上新假設）
   - B) 升級給熟悉系統的人
   - C) 先加 log 埋點，等下次發生再抓
4. **危險訊號**（看到就放慢）：
   - 「先暫時修一下」——沒有暫時，要嘛修對、要嘛升級。
   - 還沒追完資料流就提修法——你在猜。
   - 每修一處就冒出另一處問題——修錯層了。

## Phase 4：修正

1. **修根因，不修症狀**；用最小的改動消除真正的問題。
2. **最小 diff**：碰最少檔案、最少行數。不順手重構、不改相鄰程式碼的格式或註解。
3. 自己的修改造成的孤立 import／變數／函式要刪掉；與任務無關的 dead code 只提出、不刪。
4. **影響面大**（改到 > 5 個檔案）→ 先問使用者：
   - A) 照做，根因確實橫跨這些檔案
   - B) 拆開，先修關鍵路徑、其餘延後
   - C) 重新想更精準的修法
5. 影響面大的架構級修正，優先用 additive 方式（新函式＋設定開關），預設路徑行為不變。

## Phase 5：驗證與回報

1. Phase 1 的重現測試**由紅轉綠**。
2. 跑**完整測試套件**，貼輸出。不准有新的紅燈；有紅燈先單獨重跑，確認是不是環境問題，再下結論。
3. **重新走一次原始重現情境**（不只看測試），確認真的修好了。牽涉畫面就用 `browser` skill 截圖並 Read。
4. 不准說「應該修好了」——拿出證據。
5. 輸出除錯報告：

```
除錯報告
症狀：      使用者看到了什麼
根因：      實際錯在哪裡（file:line）
來由查證：  git blame／commit 結論（刻意 or 疏失，依據）
修正：      改了什麼（file:line）
回歸測試：  測試檔:行號（修正前紅、修正後綠）
證據：      測試輸出、重現結果
相關：      同區塊過往 bug、架構疑慮
狀態：      DONE | DONE_WITH_CONCERNS | BLOCKED
```

狀態定義：
- **DONE**：找到根因、已修、回歸測試先紅後綠、全套測試綠。
- **DONE_WITH_CONCERNS**：已修但無法完整驗證（偶發、需要特定環境），寫明缺什麼。
- **BLOCKED**：查完仍不清楚根因，已升級。

## 規則摘要

- 3 次修正嘗試都失敗 → 停下，質疑架構，而不是繼續換假設。
- 無法驗證的修正不要套用。
- 放寬既有測試斷言前，先做反證實驗，證明放寬的理由是真的；不准為了讓測試變綠而改斷言。
- 值得記下的教訓（非顯而易見、下次能省時間）在報告最後一行提出，由使用者決定要不要存。
