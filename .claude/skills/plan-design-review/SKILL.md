# plan-design-review — 設計計畫審查

產出是**更好的計畫**，不是一份關於計畫的文件。不改程式碼、不開始實作。
姿態：有主見但合作——找出每個缺口、說明為何重要、明顯的直接補、真正的取捨交給使用者。

## Step 0：確認審查對象（第一個動作，硬停）

第一個工具呼叫必須是 AskUserQuestion（不可用時以純文字列選項後停下）：

```
要審哪一份？
A) 目前分支的 diff
B) 我貼上或指定的計畫／設計文件
C) 指定的頁面、檔案或路徑
```

## Step 1：事前盤點

- 讀計畫、專案 CLAUDE.md、`DESIGN.md`（或同類設計系統文件；若存在，所有判斷以它為準）、設計相關待辦。
- 盤出 UI 範圍：哪些畫面、元件、互動。
- **計畫完全沒有 UI**（純後端／API／基礎設施）→ 告訴使用者「此計畫無 UI 範圍，不適用設計審查」並結束。
- 沒有設計系統文件 → 標記為缺口，以通用原則審。
- 程式碼中已有哪些 UI 模式／元件應該沿用？不要重造。

## Step 2：整體評分與聚焦

1. 給計畫一個「設計完整度」總分 0–10，並說明**這份計畫的 10 分長什麼樣**。
   例：「7/10——互動描述清楚，但缺空狀態、錯誤狀態與手機版行為。」
2. AskUserQuestion：「總分 N/10，最大缺口是 X、Y、Z。要審全部 7 個維度，還是聚焦其中幾個？」等回覆。

### 選用：參考截圖
若計畫是改版既有畫面、或有競品／參考站，可用 `browser` skill 截圖對照（桌機＋iOS webkit＋Android chromium），截完自己 Read 看過再引用。
不截圖也能完成審查；不要為了截圖而卡住流程。

## Step 3：七個維度（每維：打分 → 說明 10 分樣貌 → 補進計畫）

每個問題單獨用一次 AskUserQuestion，附建議與理由（連到下方某條設計原則）。沒問題就說「本維度無問題」。

### 1. 資訊架構
使用者第一眼、第二眼、第三眼看到什麼？補：畫面結構與導覽流程的 ASCII 圖。
限制思考：「如果只能放 3 樣東西，是哪 3 樣？」

### 2. 互動狀態覆蓋
有沒有定義 loading／空／錯誤／成功／部分完成？補狀態表：
```
功能          | LOADING | EMPTY | ERROR | SUCCESS | PARTIAL
--------------|---------|-------|-------|---------|--------
[每個 UI 功能] | [描述]  | [描述]| [描述]| [描述]  | [描述]
```
寫使用者**看到**什麼，不寫後端做什麼。空狀態是功能：要有溫度、主要行動、脈絡。

### 3. 使用者旅程與情緒弧線
補旅程表：
```
步驟 | 使用者做什麼 | 使用者感受 | 計畫有對應設計嗎？
```
三個時間尺度：5 秒（直覺印象）、5 分鐘（操作行為）、長期（回想與習慣）。
語言學習類產品特別注意：挫折點（連錯、忘記）、成就回饋、回訪動機。

### 4. AI 模板感風險
計畫描述的是具體、有意圖的 UI，還是泛用模板？把模糊描述改寫成具體決策。
- 「乾淨現代的介面」→ 沒有意義，換成字體、間距尺度、互動模式的具體名稱。
- 「帶 icon 的卡片」→ 跟其他 SaaS 模板差在哪？

**模板感黑名單**（出現即標記）：
1. 紫／靛色漸層背景、藍到紫配色
2. 三欄功能格：彩色圓圈 icon＋粗標題＋兩行說明，重複三次
3. 彩色圓圈 icon 當段落裝飾
4. 全部置中
5. 每個元素都同一個大圓角
6. 裝飾性色塊、漂浮圓圈、波浪分隔線
7. emoji 當設計元素
8. 卡片左側彩色邊框
9. 空泛標語（「歡迎來到 X」「釋放 ⋯ 的力量」「一站式解決方案」）
10. 制式段落節奏（hero → 三功能 → 見證 → 價格 → CTA，每段等高）
11. system-ui 當主要字體

**分類規則**：
- 行銷／落地頁：首屏是一個構圖不是儀表板；品牌 > 標題 > 內文 > CTA；每段只做一件事；最多兩種字體。
- App 介面：安靜的表面層次、強排版、少顏色；密集但可讀；卡片只在卡片本身就是互動時使用。
- 通用：顏色用 CSS 變數；內文 ≥ 16px、對比 ≥ 4.5:1；不可只用 placeholder 當 label；標題要貼近它介紹的段落。

### 5. 設計系統對齊
有設計系統文件 → 標出對應的 token／元件；新元件是否融入既有語彙。沒有 → 標記缺口。

### 6. 響應式與無障礙
響應式不是「手機就疊起來」：每個寬度要有刻意的版面決策。
補：各寬度規格（375／768／1024／1440）、鍵盤導覽、ARIA landmark、觸控目標 ≥ 44px、色彩對比要求。

### 7. 未決設計決策
列出會在實作時反咬的模糊點：
```
需要的決策            | 若延後會發生什麼
----------------------|--------------------------------
空狀態長怎樣？        | 工程師會上「查無資料」
手機導覽模式？        | 桌機導覽被塞進漢堡選單
```
每個決策一次 AskUserQuestion（建議＋理由＋替代方案），裁決後立刻寫進計畫。

## 設計原則（判斷依據）

1. 空狀態是功能。
2. 每個畫面都有層次：如果全部都在搶，就沒有贏家。
3. 具體勝過氛圍：說出字體、間距、互動模式的名字。
4. 邊界情況就是使用者體驗：超長名稱、零結果、錯誤、新手 vs 老手。
5. 減法預設：元素沒有賺到它的像素就拿掉。
6. 無障礙不是選配。
7. 別讓人思考：每頁要不言自明；三次不用想的點擊勝過一次要想的點擊。
8. 使用者是掃描不是閱讀；他們挑第一個看起來可以的選項——讓正確選項最顯眼。
9. 導覽的「樹幹測試」：遮掉內容只看導覽，仍知道這是哪個站、在哪一頁、有哪些主要區塊。
10. 好感水庫：隱藏資訊、格式刁難、多餘提問、強制導覽都會扣；明確主要任務、省步驟、好的錯誤恢復會加。
11. 「這感覺不對」必須能追溯到某條被打破的原則——品味是可以除錯的。

## 提問規則

- 一個問題一次 AskUserQuestion，不批次；編號「問題數字＋選項字母」（例：2A）。
- 每個選項寫：現在定義要花多少力氣、延後的風險。
- 「修法很明顯」也要使用者同意才寫進計畫。

## 必要產出與完成摘要

- **不做的事**：考慮過但延後的設計工作，每項一行理由。
- **既有可重用**：應沿用的現有元件與模式。
- **待辦提案**：每項單獨問（記入待辦／不做／這次就做）。

```
設計計畫審查摘要
盤點         | 設計系統文件狀態、UI 範圍
總分         | ＿/10 → ＿/10
1 資訊架構   | ＿/10 → ＿/10
2 狀態覆蓋   | ＿/10 → ＿/10
3 使用者旅程 | ＿/10 → ＿/10
4 模板感     | ＿/10 → ＿/10
5 設計系統   | ＿/10 → ＿/10
6 響應式/a11y| ＿/10 → ＿/10
7 未決決策   | 已裁 ＿ 項、延後 ＿ 項
```

全部 ≥ 8：「計畫設計完整。實作後用 design-review 做線上視覺 QA。」
有低於 8 的：寫明未解決項與原因（使用者選擇延後）。
