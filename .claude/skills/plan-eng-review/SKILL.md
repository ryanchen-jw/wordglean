# plan-eng-review — 工程計畫審查

審查計畫，不寫程式。每個問題都要講清楚取捨、給出明確建議，然後**等使用者裁決**，不默默替使用者決定。

## Step 0：確認審查對象（第一個動作，硬停）

第一個工具呼叫必須是 AskUserQuestion（不可用時以純文字列選項後停下等回覆）：

```
要審哪一份？
A) 目前分支的 diff（進行中的工作）
B) 我貼上或指定的計畫／設計文件
C) 指定的檔案、目錄或路徑
建議：有分支 diff 選 A，否則 B。
```

使用者回答前，不跑 git、不讀檔、不開始審。

## Step 1：蒐集脈絡

- 讀計畫本體、專案 CLAUDE.md、README、相關設計文件、TODO 清單（若有）。
- `git log --oneline -15`：同區塊若有過「審查後重構」「revert」的紀錄，該區塊審得更嚴。

## Step 2：範圍挑戰（先於所有審查段落）

逐題回答：

1. **既有程式碼**：每個子問題，現有哪些程式／流程已經部分或完全解決？能不能沿用既有產出，而不是另建平行流程？
2. **最小改動集**：達成目標所需的最少變更是什麼？哪些工作可以延後而不卡核心目標？
3. **複雜度檢查**：碰到 > 8 個檔案或新增 > 2 個 class／service ＝ 異味，挑戰能否用更少零件達成。
4. **內建檢查**：計畫引入的每個模式／基礎設施，框架或執行環境有沒有內建可用？有沒有已知地雷？（可用 WebSearch；版本相關問題查官方文件，不憑記憶）
5. **發佈檢查**：若產出新的可發佈物（套件、image、App 安裝包），建置與發佈流程有沒有寫進計畫？沒有就明列在「不做的事」。

**複雜度檢查觸發時**：停下，用 AskUserQuestion 指出哪裡過度設計、提出最小版本，問「縮減 or 照原案」。使用者回答前不進入 Step 3。

使用者一旦裁決範圍，就**完全照辦**：後面段落不再重提縮減，也不偷偷砍掉計畫中的元件。

## Step 3：四段審查（依序，一段一段來）

每段最多挑 8 個最重要的問題。每段沒有問題就說「本段無問題」並繼續——但每段都必須真的評估過，不能因為「這是策略文件」就跳過。

### 3.1 架構
- 系統設計與元件邊界、相依關係與耦合
- 資料流與瓶頸、擴展性與單點故障
- 安全架構（認證、資料存取、API 邊界）
- 每條新程式路徑／整合點：寫出一個真實的正式環境失敗情境，計畫有沒有處理
- 關鍵流程是否值得畫 ASCII 圖（放計畫或程式註解）

### 3.2 程式品質
- 模組組織與結構
- 重複（DRY）——積極指出
- 錯誤處理與遺漏的邊界情況（逐一點名）
- 過度設計 vs 設計不足（目標是「剛好夠」：不脆弱、也不預先抽象）
- 偏好明確勝過聰明
- 被修改檔案中既有的圖或註解，改完後還正確嗎？

### 3.3 測試
目標是每條新路徑都有測試。產出覆蓋圖：

```
程式路徑                                    使用者流程
[+] src/services/lesson.ts                  [+] 完成一課
  ├── submitAnswer()                          ├── [★★★ 已測] 答對流程 — lesson.e2e.ts:15
  │   ├── [★★★ 已測] 正確/錯誤/逾時           ├── [缺] [→E2E] 連點送出
  │   └── [缺]       網路中斷                  └── [缺]        答題中途離開
覆蓋：3/7 路徑（43%）  缺口：4（2 個需 E2E）
```
圖例：★★★ 行為＋邊界＋錯誤｜★★ 正常路徑｜★ 冒煙｜[→E2E] 需整合測試｜[→EVAL] 需 LLM 品質評測

單元 vs E2E 判準：
- **E2E**：跨 3 個以上元件的常用流程、mock 會掩蓋真實失敗的整合點、認證／金流／刪除資料流程
- **EVAL**：關鍵 LLM 呼叫、prompt／系統指令／tool 定義的變更
- **單元**：純函式、無副作用的內部 helper、單一函式的邊界值

**回歸鐵則**：計畫修改了既有行為且現有測試沒覆蓋 → 回歸測試列為必要項，不必問。

每個缺口寫成具體測試需求：測試檔名（照既有命名）、斷言內容（輸入 → 預期輸出）、測試類型。

### 3.4 效能
- N+1 查詢與資料存取模式
- 記憶體用量
- 快取機會
- 慢路徑或高複雜度程式

## Step 4：提問規則

- **一個問題一次 AskUserQuestion**，不批次。
- 具體描述問題，附 file:line。
- 給 2–3 個選項（合理時含「不處理」）；每個選項一行寫：工作量、風險、維護負擔。
- 一句話把建議連到上面的偏好（最小 diff、明確勝過聰明、測試完整等）。
- 編號：問題用數字、選項用字母（例：「3A」「3B」）。
- 選項差在「覆蓋多寡」時，標 `完整度 N/10`；差在「種類」時不標分數，註明「選項性質不同、不評完整度」。
- 「修法很明顯」的問題仍然是問題，仍要使用者同意才寫進計畫。

## 信心標示

每個發現標信心分數：

| 分數 | 意義 | 呈現 |
|---|---|---|
| 9–10 | 讀過具體程式碼驗證 | 正常列出 |
| 7–8 | 高信心的模式比對 | 正常列出 |
| 5–6 | 可能誤報 | 附註「中等信心，請確認」 |
| 3–4 | 可疑但可能沒事 | 放附錄 |
| 1–2 | 臆測 | 只有嚴重度 P0 才提 |

格式：`[P1]（信心 9/10）path/file.ts:42 — 描述`

**提報前驗證**：必須能引用觸發該發現的程式碼原文（file:line＋原文）。引用不出來＝未驗證，信心強制降到 4–5、進附錄。

## Step 5：必要產出

1. **不做的事（NOT in scope）**：考慮過但延後的工作，每項一行理由。
2. **既有可重用**：已部分解決子問題的程式／流程，計畫是沿用還是重造。
3. **失敗模式**：每條新路徑列一個真實失敗方式，標註 (a) 有無測試 (b) 有無錯誤處理 (c) 使用者會看到清楚錯誤還是靜默失敗。三者皆無＝**關鍵缺口**。
4. **待辦提案**：每個延後項目單獨問一次——A) 記入待辦 B) 不值得做 C) 這次就做。每項寫清楚：做什麼、為什麼、前置依賴、三個月後的人接手需要的脈絡。
5. **並行策略**（有 2 條以上獨立工作線時）：依模組列相依表，分出可並行的線與必須循序的線，標出兩線碰同一模組的衝突風險。否則寫「循序實作、無並行機會」。
6. **實作任務清單**：把裁決後的發現整理成扁平任務列表（優先度、元件、標題、來源發現、涉及檔案）。

## Step 6：完成摘要

```
- 範圍挑戰：照原案 / 已縮減
- 架構：＿個問題
- 程式品質：＿個問題
- 測試：已產覆蓋圖，＿個缺口
- 效能：＿個問題
- 不做的事：已寫（＿項）
- 既有可重用：已寫
- 待辦提案：＿項
- 失敗模式：＿個關鍵缺口
- 並行：＿條線
- 未決事項：（列出，或寫「無未決事項」）
```

使用者同意後，把裁決結果寫回計畫檔（若有）；審查本身不改任何程式碼。
