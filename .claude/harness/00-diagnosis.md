# Harness 漏水診斷書

> 本檔是其他 harness 檔的依據來源;引用格式 `00-diagnosis §N`。
> 來源:複刻自前一個專案的診斷書(該專案以本制度運作數月後的版本)。§1/§3 為通用診斷,沿用;§2 為**新專案自己的**修復清單,初始為空。
> 新專案落地後若做了自己的診斷,把日期與證據補進 §1 各痛點的「本專案證據」欄。

## §1 三大痛點與物理級阻斷方案

### 痛點 1:指揮官下場 → 主對話 context 燒毀 + 無隔離驗證

**現象**:執行長(主對話)親自做大批量讀檔與調查,寶貴的決策 context 被原始資料淹沒;實作端自己回報自己驗證,唯一防線是執行長肉眼看 git diff。

**典型證據**:
- 「進子專案實地調查」是正確的原則(不憑空派工),錯誤的是執行者:調查動作由主對話親自跑 Read/Glob/Grep,一個多專案的派工日會把數萬 token 原始碼灌進決策 context
- 驗收 = 執行長親跑 `git status` + `git diff` 讀全量改動,大型 diff 直接吃掉主對話
- 待辦清單單條任務過長,每次派工全文載入
- 驗收依賴實作端誠實回報;無任何 fresh-context 驗證機制,「改了什麼」與「宣稱改了什麼」之間沒有第三方對帳

**物理阻斷**:
1. **指揮官不下場**:調查與 diff 審閱一律派 read-only subagent(Explore),主對話只收 ≤30 行結論。量化判準見 `01-model-dispatch.md §2`
2. **隔離驗證**:實作者不得自驗;驗收由 Fresh-Context 驗收官執行 read-back + 實跑,見 `01-model-dispatch.md §5`
3. **待辦瘦身**:任務細節寫在 backlog 任務卡內,不在路由檔或每日載入的檔案裡堆長文

### 痛點 2:規則多源重複與活矛盾(single source of truth 崩壞)

**現象**:同一條規則以不同措辭存在於多處;出現「兩處說法相反」的活矛盾。弱模型會服從最後載入或最具體的那份,行為變成載入順序的函數——不可預測。

**典型證據**:
- 通用「AI 行為準則」在多個子專案 CLAUDE.md 逐字重複
- 營運樣板(如 prod 主機連線指令)在多個子專案重複
- 「sub-session 不 push」類規則散落多處 + memory 又有一條例外——弱模型讀到哪份就守哪份
- **活矛盾**:一份文件說某資料表已棄用,另一份仍列為現役
- **幻覺依賴**:子專案 CLAUDE.md 描述一套根本不存在的理想架構——弱模型照它動手 = 引入不存在的依賴
- **工具指令打架**:全域 CLAUDE.md 禁用某工具,但 system prompt 同時載入該工具的完整使用教學

**物理阻斷**:
1. **規則唯一性**:每條規則只允許存在一處,其他位置只放一行指標(`見 <path>`)。寫入 `04-knowledge-protocol.md §4`,新增規則前必先 grep
2. **層級歸位**:通用行為準則 → 全域 `~/.claude/CLAUDE.md`;workspace SOP(push/prod/回報)→ `.claude/harness/` 或 daily-brain;子專案 CLAUDE.md 只留該 repo 特有事實
3. **子專案修復清單**:見 §2

### 痛點 3:多套同職責工具並存 + Skill 觸發面過寬

**現象**:工具選擇本身變成一個需要「判斷力」的問題——這正是弱模型最弱的地方。選錯工具 = 整輪浪費 + 誤觸發副作用。

**典型證據**:
- 瀏覽器自動化同時存在多套(MCP 擴充、plugin、skill)且有多個近義 skill 並存
- 常駐 skill 清單數十個,多個 skill 描述含「即使沒明說也應主動觸發」——觸發詞寬到在不相干對話裡屬純噪音與誤觸源
- 已啟用的 plugin 與既有 skill 職責重疊

**物理阻斷**:
1. **工具路由表寫進全域 CLAUDE.md**(唯一指定,不並列選項):網頁瀏覽/QA → `browser` skill;專案 E2E 測試 → 專案內既有 Playwright;其他瀏覽器 MCP → 一律禁(例外需白紙黑字列在路由表)
2. **建議 user 執行**(需權限):停用與路由表職責重疊的 plugin
3. **skill 描述去侵略化**:「主動觸發」語句限縮到特定子專案目錄內(修 skill frontmatter 的 description,屬提案級變更)

## §3 能力極限與誠實條款

**這套 harness 能逼近但不能取代的東西**:拆解 + 隔離驗證可以讓弱模型在「有明確判準的任務」上接近高階品質(修 bug、重構、資料管線、格式化報告)。以下三類任務,弱模型「結構上」注定失敗,不是努力問題:

1. **模糊的商業美感/品味決策**(品牌視覺方向、行銷文案語氣、頁面「感覺對不對」)
2. **無 ground truth 的策略取捨**(該做 A 功能還是 B 功能、風險偏好、定價)
3. **跨領域的第一性原理判斷**(「這個結果好到不像真的」的直覺)

**弱模型遇到上述情境的標準應對**(違反即為制度違規):
- **禁止**:自行拍板然後執行;用「業界慣例」「一般而言」語句掩蓋不確定性
- **必須**:產出 2-3 個具體選項(每個附可比較的樣本/mockup/數據)→ 用 `AskUserQuestion` 交 user 選 → 只執行被選中的那個
- **量化熔斷**:若一個決策無法寫出「事後可驗證的成功判準」(例:無法寫成測試、無法寫成數字門檻、無法寫成 checklist),它就屬於品味決策,交 user
- **不確定的事實**:先查(repo / DB / 文件);查不到 → 在產出中標 `⚠️ 未驗證:<陳述>`,禁止寫成肯定句
