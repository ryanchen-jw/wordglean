# 標準化派工 Prompt 模板

> 用法:執行長複製對應模板 → 填 `{{...}}` → 派出。每個 `{{...}}` 都必填;填不出來代表你(執行長)還沒調查清楚,先回去補調查。
> (本檔模板內的小寫/中文 `{{...}}` 是**每次派工的填空欄**,不是專案層佔位;專案層佔位一律大寫蛇形,如 `C:/Projects/LinguaApp`。)

## §0 共用規則(適用全部模板)

- **Context 引入**:給「路徑 + 該讀哪段 + 為什麼」,不貼檔案內容(subagent 自己會讀,貼了反而占它的 context 又可能過期)
- **回報上限**:≤30 行;代碼引用一律 `路徑:行號`、內文貼碼 ≤10 行
- **速查卡**:每個模板結尾都帶 `02-judgment-matrix.md §4` 速查卡(已內嵌)
- **時間錨**:涉及日期的任務,寫死絕對日期(subagent 沒有「今天」的可靠概念)

```
【要回答的問題】(逐條,可勾選)

```

## §3 模板 C:代碼重構

> 派給:general-purpose subagent(預設主力模型)。重構鐵律:**行為不變,有量化證據**。

```
【任務】重構 {{目標模組/函式}}:{{一句話目的,例:消除三處重複的資料載入邏輯}}
【動機】{{為什麼現在重構;引用踩坑或效能證據}}
【行為凍結證明】(重構的核心驗收)
1. 重構前先跑 {{測試指令}} 記錄結果(全綠才開始;有紅的先回報)
2. 重構後同指令結果必須完全一致(相同 pass 數、相同 skip 數)
3. {{若涉及效能:benchmark 指令 + 前後數字,退步 >5% 即失敗}}
【範圍】
- 只動:{{檔案清單}}
- 公開介面(函式簽名/CLI 參數/輸出格式)一律不變;要變就停下回報
【驗收條件】
1. 行為凍結證明 1-3 全過
2. {{量化目標,例:重複代碼三處合一、不再有寫死的版本字串}}
3. git diff 無「順手」改動(格式化、改註解、重新命名無關變數都算越界)
【回報格式】場景 2 + 前後對照表(行數/測試數/benchmark 數字)。
【判準速查卡】(同模板 B,略)
```

## §4 模板 D:代碼審查 / 隔離驗收

> 派給:**全新** Explore subagent(需實跑測試時用 general-purpose)。
> 鐵律:驗收官只拿驗收條件與路徑,**不給實作者的任何說法**(防錨定);執行長派工時將 `08-smell-baseline.md` 全文貼於 prompt 末。

```
【任務】你是驗收官,對以下改動做隔離驗收。你沒有參與實作;每條結論都要有你親自跑出/讀到的證據。
【被驗改動】{{`<Project>` 分支 `worktree-<topic>` 相對預設分支的 diff／工作區未 commit 改動}}
【原始驗收條件】(逐條核對,這是唯一標準)
1. {{條件1 原文}}
2. {{條件2 原文}}
【必做程序】
1. Read-back:重讀每個被改檔案,逐條核對上列條件
2. 實跑:{{測試/build 指令}} 自己跑,不採信轉述輸出
   ⚠️ **容器 bind-mount 假綠陷阱**:長駐容器掛的是**主工作區**,不是 worktree——`docker exec <長駐容器> <測試指令>` 測到的是主分支、整輪假綠。驗 worktree 一律用「一次性容器掛 worktree」或 `docker cp` 進隔離路徑,並先 grep 佐證讀到的是分支碼。共用測試 DB 要改用**專屬拋棄庫**(自取獨一名)。前端 dev server **埠被占會自動遞增**,要用 `netstat`／server log 確認實際綁定埠,不可用「curl 預期埠得 200」判就緒(會連到沒死透的舊 server)
3. 越界檢查:git diff --stat 有沒有條件之外的檔案
4. 抽查誠實性:實作回報若引用行號,抽 2 個核對是否真在該處
5. TDD 閘(fix 類必查):repo 裡有重現該 bug 的新測試,且實作回報附「先紅後綠」輸出證據;缺任一 → FAIL(例外同派工條款:無單元測試框架的子專案查驗證腳本;純表現層 fix 查前後截圖對照)
6. **副作用閘**(凡改動涉及對外真實寫入/呼叫外部服務者必查):列出每一條「會打到正式外部系統」的程式路徑(發文/推播/寄信/扣款/刪除),逐條問「**它靠什麼機制保證測試時打不到正式環境?**」。答案若是環境狀態(「dev 沒有憑證」「那張表現在是空的」「那個變數只有 prod 才有」)→ **FAIL**:環境會變,註解不會紅。必須是程式碼裡的顯式拒絕(預設 deny、要真打得顯式開啟)且有測試證明守衛真的會擋。
   ⚠️ 典型事故形狀:verify 案例帶 `--confirm` 走真模式,安全性只寫在註解裡的一句「dev 沒有正式憑證」;日後有人把真憑證裝進 dev 設定,前提失效,該案例**真的對正式帳號發出測試內容**。同輪的「未帶 --confirm ⇒ 零對外呼叫」斷言完全沒被違反——它驗錯了軸。
7. **守衛自己的紅證**(有守衛/護欄/斷言的改動必查):紅證不能只對「被守衛的東西」做,必須對**守衛自己**也做一次——把守衛該擋的東西真的弄壞,看它會不會紅。驗完還原並比對雜湊。守衛沒被證明會紅 = 沒有守衛。
   ⚠️ **出網／對外寫入守衛有一個不可跨越的例外**:**不准用「關掉守衛,看是不是真的會打出去」來證明它有效**——那個證明動作本身就是事故。
   正確的紅證方向是**單邊的**:把「讓守衛不該擋」的條件移除(例如拔掉測試 seam),確認它**仍然擋**並拋出預期例外。守衛「不擋時會發生什麼」不需要證明——那正是它存在的理由。同理適用於寄信、扣款、刪除等一切對外副作用。
   ⚠️ 常見同形狀:擋板只靠「dev 沒有憑證」;健檢只靠一個不跨程序/主機邊界的環境變數;「CI 有跑到測試」的守衛比對整份檔案字串,被註解裡的字串滿足(把真正跑測試那行刪掉照樣綠)。共同點=**守衛的有效性依賴一個沒有被任何東西保證的前提,而那個前提平常剛好成立,所以看起來一直是綠的**。
8. Standards 檢查:對照本 prompt 末的 08 smell 基線掃 diff;發現列「觀察」供執行長裁量,不影響 PASS/FAIL(基線是 judgement call 非硬違規)
【回報格式】
- 每條驗收條件:✅/❌ + 一行證據(指令輸出關鍵行或 路徑:行號)
- 越界檔案清單(無則寫「無」)
- 結論:PASS / FAIL(任一 ❌ 即 FAIL)
- FAIL 時:退件理由逐條、可直接轉給實作端(防錨定:理由不含解法)
- 末段附「verdict 摘要」(≤6 行:結論 PASS/FAIL、關鍵數字、重跑指令)——供執行長直接落檔統一驗證報告(harness/07)
```
