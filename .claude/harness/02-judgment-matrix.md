# 判斷力外化矩陣

> 用法:卡住、想宣告完成、或想問 user 之前,逐條肉眼比對。
> 每條有【信號】(可觀察的事實)、【正例】(該怎麼做)、【反例】(弱模型的典型錯誤)。

## §1 換路徑信號 —— 方向錯了,立刻停、換路徑

命中任何一條 → 停下手,回到上一個決策點重新選路(或升級,見 `01-model-dispatch.md §4`)。換路徑,不原地重試:

### 1-1 錯誤訊息在變,但不是在變好
【信號】連續兩次修復後,測試仍紅,且**錯誤訊息換了一種**(不是同一個 assert 逐步逼近,而是東牆補西牆)。
【正例】修型別錯 → 第二輪變成索引對不齊錯 → 停手,回頭重讀資料流上游,發現真因是來源 schema 變了;改一處上游,兩個錯同時消失。
【反例】繼續在下游各補一個型別轉換 / 重新對齊,測試終於綠了——埋下多個掩蓋真因的補丁,下次資料一變全部炸開。

### 1-2 蹺蹺板:修 A 壞 B
【信號】讓測試 A 過的改動使原本綠的測試 B 變紅,反之亦然,往返 ≥ 2 次。
【正例】停手。把 A、B 兩個測試各自斷言的行為寫成兩句話並列——通常會發現兩者對同一函式有矛盾期待,這是**需求或設計問題**,按 §3 熔斷問 user。
【反例】把測試 B 改鬆(改 assert、加 skip)讓兩邊都綠。刪除或弱化既有測試來讓自己的改動通過,永遠是換路徑信號,不是解法。

### 1-3 開始遷就:改框架/函式庫/共用碼來配合自己的新代碼
【信號】為了讓新功能動,發現自己在改 site-packages / node_modules、第三方 skill 本體、或其他專案共用 script 的行為。
【正例】停手。共用碼要改 = 影響面超出本任務 → flag 給執行長,把「共用碼為何擋路」寫清楚,由執行長決定開新任務或換作法。
【反例】直接改共用腳本的預設值讓自己的任務能跑——其他呼叫方靜默拿到錯誤行為。

### 1-4 diff 膨脹超過需求量級
【信號】`git diff --stat` 行數超過任務量級:fix 類 > 100 行、單 stage feat > 300 行(皆不含測試檔與自動生成檔),或超出派工 prompt 明訂的檔數/行數上限。
【正例】停手,`git stash`,重新只做最小改動。
【反例】「反正都改了」繼續往下寫,回報時說「順便重構了某模組」——執行長無法審,整包退件。

### 1-5 Mock 越疊越多才能讓測試過
【信號】一個測試需要 ≥ 3 層 mock/patch 才能跑,且每修一次要再加一個 mock。
【正例】停手。要嘛被測單元切分錯了(重新拆),要嘛這屬於整合測試(改用真依賴的 fixture / testcontainer)。
【反例】mock 到測試全綠——測試從此只測 mock,對真實行為零保護。

### 1-6 開始猜路徑/猜 schema/猜 API
【信號】連續 2 次引用的檔案路徑、表名、欄位、函式簽名不存在(NameError / FileNotFound / column does not exist)。
【正例】停止產出,切換成純調查:Glob/Grep/列 schema 把實際存在的東西列出來,對照後再繼續。
【反例】換一個「聽起來更合理」的名字再猜一次。連續猜錯兩次 = 你的世界模型與這個 repo 不同步,再猜只會更歪。

## §2 完成判準 —— 全部命中才可宣告「完成」

宣告完成前逐條自檢;交付回報必須附這張表的勾選結果:

- [ ] **驗收條件全綠**:派工三件套裡的每條驗收條件都 ✅,且證據是**本輪實跑**的輸出(不是「剛才跑過」的記憶)
- [ ] **測試**:改動涉及的測試通過;紅→綠有證據、AC 有對應測試(細則與例外=daily-brain 派工條款 TDD 節)
- [ ] **UI 視覺走查(has-ui)**:此關是**執行長層閘**(daily-brain Step 5.2、發生在 worker 回報之後)——worker 自檢此項一律標「N/A(待執行長走查)」;任務要走查 P0 全清才算真正結案(見 `harness/05-ui-visual-review.md`);非 has-ui 免此條
- [ ] **app 視覺 smoke(涉可見 UI 變更)**:已用真瀏覽器跑關鍵狀態、截圖存本地報告(見 `harness/06-uiux-visual-smoke.md`);**報告未上雲**;純邏輯/無 UI 免
- [ ] **無越界**:`git diff --stat` 中每個檔案都能對應到驗收條件;無關檔案 0 個
- [ ] **無殘留**:無 debug print、無註解掉的舊碼、無 TODO(有就列進回報的「未盡事項」)
- [ ] **環境還原**:臨時服務關閉、測試資料清掉、`.env` 復原(比照 `session-report-spec.md` 場景 5)
- [ ] **回報合規**:按 `session-report-spec.md` 對應場景格式;TL;DR 3 行;代碼引用只給 `路徑:行號`
- [ ] **可追溯**:能對 diff 中任一行回答「這行對應需求的哪一句」

【正例】某報表高度 fix:diff 1 檔 3 行、新增 1 個高度斷言測試、測試貼最後 3 行綠、回報 5 行。這就是滿分交付,不需要更多。
【反例】「已完成,測試應該都會過」——「應該」= 未實跑 = 未完成。「大部分測試通過,剩下的失敗與本次無關」——需列出每個失敗測試名並證明失敗在改動前就存在(`git stash` 後重跑同樣紅),否則不算完成。

## §3 熔斷條件 —— 停止自主作業,問 user

命中任何一條 → 停,用 `AskUserQuestion`(或 session-report-spec 場景 3 格式)附選項與建議問 user。**熔斷不是失敗,靜默硬幹才是失敗。**
**問前分流**:事實問題(環境可查——檔案/DB/git/log)自查不問;決策問題才問人;每題附推薦答案與理由,讓 user 可一鍵同意。

| # | 條件 | 判定方式 |
|---|---|---|
| 3-1 | 破壞性/不可逆操作未被明示授權 | DELETE/DROP/TRUNCATE、rm 非自建檔、push --force、真錢操作、prod 環境變更。授權必須是**本次任務內**的白紙黑字,上週的授權不延續 |
| 3-2 | 需求存在兩種解讀,且選錯會浪費 > 30 分鐘工作量 | 能寫出兩句互斥的解讀句子,就是真歧義;寫不出來就不是,自己選並在回報註明假設 |
| 3-3 | 同一件事在當前層級連錯 2 次、升級後又連錯 2 次 | 計數定義見 `01-model-dispatch.md §4`(每層最多 2 次、升級歸零) |
| 3-4 | 要動到凍結物 | `docs/spec/requirements.md` 已拍板條目、單字資料授權分界（data/ 為 CC BY-SA）、任何標注「執行長拍板」的決定 |
| 3-5 | 品味/商業決策 | 判定法:寫不出事後可驗證的成功判準(測試/數字門檻/checklist)→ 就是品味決策 → 出 2-3 個具體選項附樣本讓 user 選(`00-diagnosis.md §3`) |
| 3-6 | 發現的現實與制度檔矛盾 | 例:CLAUDE.md 說某表/某 API 已棄用但程式仍在寫入或呼叫。回報矛盾本身、由執行長裁決 |
| 3-7 | 結果好到不像真的 | 指標突然翻倍、測試從大片紅瞬間全綠、效能提升 10 倍——先假設自己錯了:查快取、查是否跑錯資料/環境、查是否測到舊版本;查完仍好,附上排查過程再回報 |

【正例】(3-7)效能測試突然快 10 倍:先查是否命中快取、是否打到空資料庫、是否測到主工作區而非分支,把排查證據附在回報裡。
【反例】直接回報「大突破!」——執行長被迫用自己的 context 重查,等於驗收成本轉嫁。

## §4 判準速查卡(派工時可整段貼給 subagent)

```
停下換路徑:錯誤訊息換型不收斂 / 修A壞B / 想改共用碼遷就自己 / diff 超量級(fix>100行/feat單stage>300行) / mock≥3層 / 猜錯路徑或schema 2次
宣告完成前:驗收全綠(本輪實跑) / 有新測試(fix 先紅後綠;純表現層 fix 以前後截圖對照代替) / diff 無越界 / 無 debug 殘留 / 環境還原 / 涉UI變更附視覺smoke本地報告(禁上雲);05 走查關屬執行長層、worker 標 N/A 不自勾 / 回報合規 / 每行可追溯
必須問人:未授權的破壞性操作 / 真歧義且錯了浪費>30分 / 每層重試滿2次 / 動凍結物 / 寫不出驗證判準的決策 / 現實與文件矛盾 / 好到不像真的
```
