# 跨專案時間與時區規約

> 適用:所有子專案寫、存、傳、算、顯示時間的程式碼。各子專案 CLAUDE.md 只放指向本檔的一行,不重抄。
> 本檔以「業務時區」`Asia/Taipei`(IANA 名,例 `Asia/Taipei`)、`+08:00`(例 `+08:00`)書寫。
> ⚠️ 原制度的業務時區**沒有夏令時**;若新專案的業務時區或使用者分布有夏令時/多時區(語言學習 App 常見全球使用者),§總則與第 4、6 條需改寫成「以使用者時區為準」——見 `_reports/harness-port-notes.md` 待決條款。

## 總則

**存與傳用 UTC,算「哪一天」與給人看用業務時區(Asia/Taipei)。** 時差寫錯通常不會自己露餡——錯法是「業務時區凌晨那幾小時落到前一天(或後一天)」,平常測不到,只能靠下面的寫法與測試守住。

## 九條

1. **存**:新的時間欄一律帶時區型別(如 PostgreSQL `TIMESTAMPTZ`)。沿用 naive 欄位時,在欄位註解寫明它是哪個時區,且同一欄只能有一種寫入時區;改口徑時記下分界時點、舊列不回填則寫明。
2. **取現在**:寫 `datetime.now(UTC)`(要業務時區就 `datetime.now(ZoneInfo("Asia/Taipei"))`),不寫裸 `now()`／`utcnow()`,也不依賴容器或主機的 TZ 設定(prod 容器與主機常是 UTC)。
3. **傳(API)**:回應裡的時間戳一律帶 `Z` 的 UTC。用共用序列化型別統一輸出(（待定）),並有守衛測試,不在服務層自己 `isoformat()`。
4. **算日曆日**:判斷「屬於哪一天」(到期日、續訂日、日額度、連續學習天數、日界查詢)一律先換成業務時區再取日期:Python `x.astimezone(LOCAL_TZ).date()`,SQL `timezone('Asia/Taipei', col)`;查詢邊界在程式端算成業務時區 00:00 再轉 UTC。
5. **前端換算**:一律經單一工具模組(（待定）,`Intl.DateTimeFormat` 固定 `timeZone`),不用 `toISOString().split('T')[0]`、字串切片或瀏覽器本地時區取日期。
6. **顯示**:給使用者與管理員看的時間**預設就是業務時區、不另標時區**。只有兩種情況要標:畫面上**同時出現排程設定與時刻**、可能被誤讀成別的時區時標「(台北)」;以及**顯示的是 UTC** 時必須標明(`Z` 或 `UTC`)。
   **機器讀寫的時間戳**(log 前綴、部署與備份紀錄、job summary)一律 ISO-8601 UTC 帶 `Z`:`date -u +%Y-%m-%dT%H:%M:%SZ`。shell 判「是否業務時區某時段」要先顯式換算,並加偏移守衛——Windows Git Bash 缺 tzdata 時 `TZ=<IANA 名>` 會**靜默退回 UTC**,要用 POSIX 形式(例:`TZ=CST-8 date`)並檢查輸出偏移。
7. **排程**:自建排程一律顯式帶時區——APScheduler `CronTrigger(..., timezone=...)`、以 UTC 寫的 cron 要註明業務時區時刻、shell cron 腳本內顯式 `TZ=`;並用反射真實註冊表的測試守住(勿拆)。
8. **跨 repo 讀**:讀別的專案寫的表時,時區語意集中在讀取端**一個**轉換點;來源改成帶時區後,這個點應自然變成 no-op。
9. **測試**:期望值用手算字面值(例:`2026-10-01T20:00:00Z` → `+08:00` 的日期 `2026-10-02`),測資要落在業務時區凌晨的跨日窗口;時間敏感的測試注入固定的「現在」,不讀牆上時鐘(讀牆上時鐘的測試會在一天中某些時段假紅),並在 UTC 與業務時區兩種 TZ 下各跑一次。

## 寫法範本

- Python 私有常數:`_LOCAL_TZ = ZoneInfo("Asia/Taipei")`(各檔自有一份即可,不為此建共用 helper)
- naive 值先補 UTC 再換算:`(x if x.tzinfo else x.replace(tzinfo=UTC)).astimezone(_LOCAL_TZ)`——只在來源可能是 naive 時需要
